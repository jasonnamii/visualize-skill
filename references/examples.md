# Examples — 모드별 사용 예시

one-shot-graph는 **논리 엔진**이다. 시각 산출은 하지 않는다.
DIAGNOSE(프레임 추천) / DESIGN(프레임 슬롯 채움) 2모드.

---

## DIAGNOSE — 프레임 추천

### 예시 1 — 플랫폼 사업 본질

**입력**: "C8 사업 본질을 압축하고 싶어"

**출력**:
```
✅ 결론 · Multi-Flywheel 1순위
논리: 크리에이터·팬·플랫폼 3개 자기강화 루프가 서로를 구동
      → 단일 플라이휠로는 3주체 상호 구동 구조 표현 불가

대안:
· Two-sided Market — 크리에이터-팬만 조명하고 플랫폼을 단순 중개로 볼 때
· Capability Stack — 경쟁우위(왜 우리가 이기는가)가 핵심 질문일 때

➡️ 다음 · 채택하면 DESIGN으로 전환 (3루프 노드 채움)
```

---

### 예시 2 — 리텐션 진단

**입력**: "리텐션이 안 좋아. 어떤 프레임?"

**출력**:
```
✅ 결론 · Hook Model 1순위
논리: 리텐션 = 재진입 문제 = 습관 형성 루프 진단
      Trigger·Action·Reward·Investment 4단계 중 어디가 약한지 본다

대안:
· Journey Map — 이탈 포인트·감정곡선이 우선일 때 (정성 데이터 有)
· Funnel — 1회 전환 누수 관점 (재진입 아님)

⚠️ 맹점 · Hook은 재진입이 가치 본질인 제품만 적용. 1회성 구매·거래는 부적합
```

---

### 예시 3 — 사업 본질이 모호할 때

**입력**: "우리 사업 뭘로 설명해야 할지 모르겠어"

**출력**:
```
✅ 결론 · 본질 질문부터 1회 역질문
7대 본질 질문 중 어디에 해당:
· 왜 존재? → JTBD
· 왜 성장? → Flywheel/Loop/NSM
· 왜 계속 쓰지? → Hook/Journey
· 왜 돈 되지? → Unit Economics/Capability
· 왜 우리가 이김? → Capability/Control Point
· 어디서 깨짐? → Funnel/Journey
· 시장 어떻게 바꿈? → Value Chain/Unbundling

답 1개 확정되면 프레임 1~2개로 수렴
```

## DESIGN — 프레임 슬롯 채움

### 예시 4 — Hook Model 빈 슬롯 설계

**입력**: "Hook Model로 우리 앱 설계하고 싶어. 콘텐츠 큐레이션 서비스"

**출력**:
```
Hook Model 4단계 명세

| 단계 | 역할 | 후보 채움 |
|------|------|----------|
| Trigger | 재방문 유발 | 외부=푸시 알림 / 내부=지루함 감지 |
| Action | 최소 행동 | 한 번 스와이프로 콘텐츠 1개 소비 |
| Reward | 가변 보상 | 콘텐츠 품질 랜덤성 + 좋아요 카운트 |
| Investment | 사용자 투입 | 북마크·취향 학습·팔로우 |

⚠️ 맹점 · Reward의 가변성이 약하면 Hook 전체가 작동 안 함 (도파민 스파이크 없음)
         → Reward 설계가 가장 중요
➡️ 다음 · 각 슬롯 구체화 후 리텐션 지표(D1·D7·D30)로 검증
```

---

### 예시 5 — Flywheel 구성 설계

**입력**: "아마존식 플라이휠을 우리 사업에 대입하면?"

**출력**:
```
Flywheel 4~6 노드 명세

필수 조건 확인:
· 출력이 다시 입력을 증폭하는가? (자기강화)
· 한 바퀴 돌수록 다음 바퀴가 빨라지는가? (관성·복리)

노드 후보 (사업 맥락 필요):
· 노드 1: 무엇이 노드 2를 강화하는가?
· 노드 2: ...
· 노드 N: 노드 1로 어떻게 돌아오는가? ← 이게 안 닫히면 플라이휠 아님

⚠️ 맹점 · 루프가 안 닫히면 그냥 선형 프로세스. 퍼널이 정직
➡️ 다음 · 루프 폐쇄 확인 후 각 노드의 구체 액션·지표 정의
```

---

### 예시 6 — 프레임 결합

**입력**: "성장도 설명하고 수익성도 설명하고 싶어"

**출력**:
```
✅ 결론 · Flywheel + Unit Economics 결합
논리: 성장(Flywheel)과 수익(UE)은 독립 질문 → 단일 프레임 부족
     두 본질 질문이 공존하면 결합이 정직

결합 방식:
· Flywheel의 각 노드에 Unit Economics 기여를 라벨링
· 예: "리뷰 증가" 노드 → LTV 증가 기여도 표시
· 두 프레임이 서로를 보강, 한 장에 담기 어려우면 2장 분할
```

## FAIL 사례

### ✗ 안티 예시 1 — 프레임 강요

**입력**: "그냥 예쁜 도식 하나 만들어줘"

**잘못된 응답**: 임의 프레임 선택 후 슬롯 채움

**올바른 응답**:
```
본질 질문 역질문 1회 —
"이 도식이 무엇을 압축해서 보여줘야 하는가?"
· 작동원리? → Flywheel·Loop
· 누수 진단? → Funnel
· 시장 위치? → Positioning Map

답 없으면 진행 ✗ (절대규칙 1)
```

---

### ✗ 안티 예시 2 — 프레임 변별 실패

**입력**: "양면시장이니까 Two-sided Market으로 그려줘"

**잘못된 응답**: 즉시 수용

**올바른 응답**:
```
Two-sided vs 가치사슬 vs Multi-Flywheel 변별 필요:
· 공급자·수요자 모두가 고객(양쪽 수수료·가치 흐름)? → Two-sided
· 공급자가 원료 공급에 가까운 B2B? → 가치사슬
· 플랫폼 + 크리에이터 + 팬 같은 3주체 물림? → Multi-Flywheel

답에 따라 프레임 재선택
```

---

### ✗ 안티 예시 3 — 노드 과부하

**입력**: "생태계맵에 관련 주체 20개 다 넣어줘"

**잘못된 응답**: 20개 모두 넣음

**올바른 응답**:
```
한 장 한계: 5~9 노드(의사결정), 9~15(시스템맵)
20개 = 한 장 부적합

대안:
· 핵심 5~9 주체로 축약 (영향력·거래량 기준)
· 계층 분할 (1층=핵심 / 2층=세부)
· 생태계맵 대신 Multi-Flywheel로 루프 구조 강조
```
